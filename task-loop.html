//WHY  THE PROBLEM THIS SOLVES[ + ]

Agents forget. Wikis rot. Diffs bloat.

Without a loop, a coding agent re-reads the repo every chat, guesses domain words, ships extra abstractions, and files nothing back. The next ticket starts from zero. Task-loop is the sequence that stops that. The three pieces under it are how memory actually compounds.

WITHOUT A GRAPHCODE

The agent greps by vibe, opens twenty files, and still misses the call path. Orientation is paid again on every task.

WITHOUT A WIKIDOMAIN

Withdraw vs delete, t0 vs t1, house rules live in Slack and people's heads. The agent invents synonyms. Humans abandon wikis because bookkeeping is boring — that is exactly what the model is good at.

WITHOUT SKILLSPROCESS

Each chat invents a workflow. Some runs skip tests. Some over-build. A skill is a short markdown playbook the agent re-reads so the sequence stays the same.

What the loop sits on

These are not our internal services. They are public tools and a pattern. You install them on your machine, point them at your repos, and the loop tells the agent when to use which one.

LAYER_01 · CODE MAP
Graphify
a knowledge graph of the repo
What
Open-source CLI that turns a codebase into a queryable graph: classes, methods, files, call paths. Output lives in graphify-out/ next to the repo. The agent asks explain, path, and query instead of touring files.
Why
Code relationships are structural. Grep finds a string; a graph finds “what calls this.” After a change, graphify update . keeps the map cheap for the next task.
Get
github.com/Graphify-Labs/graphify · site graphify.com
PyPI package is graphifyy (two y’s). The command is still graphify.
LAYER_02 · DOMAIN MEMORY
LLM wiki
Karpathy pattern · browsed in Obsidian
What
A folder of markdown the agent compiles and maintains: summaries, glossary, gotchas, subsystem maps. You curate sources and ask questions. The agent does the bookkeeping. There is no “Second Brain app” to download — that name is just one vault. Yours can be called anything.
Why
RAG re-discovers knowledge on every question. A wiki compiles it once and keeps it current. Cross-links already exist. Contradictions are already flagged. The next Grill/Triage reads glossary.md and gotchas.md instead of guessing.
Get
Pattern (copy into the agent): Karpathy llm-wiki gist

LAYER_03 · HOW THE AGENT WORKS
Skills
markdown playbooks in Cursor
What
Small SKILL.md files the agent loads when the work matches. task-loop is the sequence. The others own one job: smallest diff, definition of done, domain language, filing a lesson.
Why
Without skills, every chat invents process. With them, Intent always comes before Act, Verify is a command that can fail, and a reusable trap lands in gotchas.md.

How they connect

You talk to the agent. The loop decides the step. Each step uses one layer. Missing graph or wiki is fine — skip that layer, do not fake another team's stack.

=== AGENTS.md ===

# LLM wiki — librarian schema

This vault is a Karpathy-style LLM wiki: an incrementally built, interlinked markdown knowledge base that sits between you (the human) and your raw sources. You curate sources and ask questions. The agent does all the bookkeeping: summarizing, cross-referencing, filing, and keeping the wiki consistent.

Obsidian is the IDE. The agent is the programmer. The wiki is the codebase.

Name the vault whatever you want. There is no product called Second Brain to download.

## Layers

1. **`raw/`** - immutable source documents (articles, papers, transcripts, notes). The agent reads from here but NEVER edits these files. Source of truth. Images live in `raw/assets/`.
2. **`wiki/`** - agent-owned markdown. Summaries, entity pages, concept pages, an overview, syntheses. The agent creates and maintains everything here.
3. **Schema** - this file. Conventions + workflows. Co-evolves over time.

## Directory layout

- `raw/` - immutable sources (`raw/assets/` for images)
- `wiki/sources/` - one summary page per ingested source
- `wiki/entities/` - people, orgs, tools, products
- `wiki/concepts/` - ideas, methods, topics
- `wiki/projects/<name>/` - hand-edited per-repo dev knowledge (overview, glossary, gotchas, subsystems, ticket-checklist, decisions). Replace `<name>` with the git folder name (example: my-app). Distinct from Graphify mirrors.
- `wiki/handoffs/` - optional Cursor session handoff documents
- `wiki/overview.md` - the evolving top-level synthesis
- `projects/<name>/` - optional mirrored Graphify code-graph wikis. Do not hand-edit.
- `inbox/` - quick capture, triaged later
- `index.md` - content catalog (read FIRST on every query)
- `log.md` - append-only chronological record
- `_templates/note.md` - Obsidian note template

## Page conventions

Every wiki page starts with YAML frontmatter, then a one-line summary, then content:

```markdown
---
type: source | entity | concept | synthesis
tags: [topic1, topic2]
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: ["raw/some-article.md"]
---

# Page Title

**Summary**: One sentence the agent reads to decide relevance.

## Content

...

## Related

- [[Other Page]]
```

Rules:
- Use `[[wikilinks]]` to connect pages. A well-linked graph beats a flat folder.
- Keep pages focused. Split a page covering multiple distinct topics.
- Use consistent terminology. Add an alias line if a concept has multiple names.
- Every claim drawn from a source cites that source (path under `raw/` or a URL).

## Operations

### Ingest

When a new source is added to `raw/`:
1. Read the source.
2. Discuss key takeaways with the user (unless batch mode).
3. Write a summary page in `wiki/sources/`.
4. Update or create relevant `wiki/entities/` and `wiki/concepts/` pages - integrate, do not just file. Flag where new data contradicts existing claims.
5. Update `index.md`.
6. Append one line to `log.md`: `## [YYYY-MM-DD] ingest | Title`.

A single source typically touches 10-15 pages.

### Query

1. Read `index.md` first to locate candidate pages.
2. Read those pages; follow `[[wikilinks]]`.
3. Answer with citations to the pages/sources used.
4. **File good answers back** as new wiki pages when they are reusable (a comparison, an analysis, a discovered connection). Explorations should compound, not vanish into chat.

### Compound (dev fixes)

After non-obvious bug fixes or features, file reusable patterns — not every ticket. See the `compound-fix` skill. Default target: `wiki/projects/<name>/gotchas.md` (example: `wiki/projects/my-app/gotchas.md`).

### Grill (domain language)

Before triage when vocabulary is fuzzy, use the `grill-with-docs` skill. Canonical terms go in `wiki/projects/<name>/glossary.md`; hard-to-reverse choices in `wiki/projects/<name>/decisions/`. Not in repo `CONTEXT.md`.

### Handoff (session transfer)

When the user says `/handoff` or asks to save session context for a fresh chat, write to `wiki/handoffs/YYYY-MM-DD-<slug>.md` with YAML frontmatter (`type: handoff`). Update `index.md` (Handoffs section) and append `log.md` (`## [DATE] handoff | Title`). Do not use `/tmp` or project `HANDOFF.md` unless the user explicitly requests project-root output.

### Lint

Periodically health-check the wiki:
- Contradictions between pages
- Stale claims superseded by newer sources
- Orphan pages (no inbound links)
- Important concepts mentioned but lacking their own page
- Missing cross-references

## index.md and log.md

- `index.md` is **content-oriented**: a catalog of every page with a link and one-line summary, grouped by category. Updated on every ingest. Read it first when answering.
- `log.md` is **chronological**: append-only. Keep the `## [YYYY-MM-DD] type | Title` prefix so `grep '^## \[' log.md | tail -5` works.

## Hard rules

- NEVER fabricate. If a fact is missing, say so or leave a `_` placeholder - do not invent.
- NEVER edit files under `raw/`. They are immutable.
- NEVER hand-edit `projects/` - it is regenerated from Graphify graphs.
- Cite sources for every non-obvious claim.
- **Compressed output is for chat answers ONLY.** Everything written INTO this vault (wiki pages, `index.md`, `log.md`, summaries) must be full, human-readable prose. The vault is a durable artifact browsed in Obsidian; compressing it corrupts readability and cross-references.

## Routing (for the agent)

- Knowledge / research / personal / "what do I know about X" -> this wiki.
- Code / architecture / "how does this codebase work" -> Graphify (`graphify explain` / `path` / symbol-seeded `query` on the repo graph, or `projects/<name>/` here if a mirror exists).
- Domain rule / prior lesson -> `wiki/projects/<name>/glossary.md` + `gotchas.md` + `subsystems.md`.
- Prompted implementation work -> `task-loop` skill (`ticket-loop` is an alias).

- Domain rule the task did not explain
- Same area broke before
- Dead-end approach (A failed, B worked)
- Non-obvious edge case

## Skip filing when

- Typo, rename, formatting
- Fully described in ticket + obvious code change
- One-off env/local config

## Task workflow

Follow the `task-loop` skill (`ticket-loop` is an alias). A prompt is a task; Jira is optional.

1. Intent from the prompt or ticket. Non-trivial: `unlazy` gates before Act.
2. **Grill** (when domain language is fuzzy): `grill-with-docs` → vault `wiki/projects/my-app/glossary.md`. Skip for literal stack traces.
3. **Triage:**
   - Stack trace / error names a file or string → Grep/Glob that literal
   - Cross-service flow, no path → `graphify query "<ServiceClass> <method>"` or `graphify path "A" "B"`
   - Domain rule / prior lesson → `glossary.md` + `gotchas.md` + `subsystems.md`
4. Act (ponytail); verify per `wiki/projects/my-app/overview.md` **Verify** (or inferred stack).
5. `graphify update .` after code changes.
6. Reusable gotcha → **compound-fix** → `wiki/projects/my-app/gotchas.md`. Skip routine one-liners.

## What not to do

- Do not dump every ticket into the wiki — file **patterns**, not diffs.
- Do not hand-edit `graphify-out/` or vault `projects/my-app/` (mirrors).
- Do not run graphify with ticket IDs or vague symptoms — seeds must be code symbols.
- Do not store domain glossary in repo `CONTEXT.md` — use the vault `glossary.md`.

Intent → Act → Verify

Solid lines are the happy path. Dashed ember lines are the repair cycle: a failed Verify goes to Repair, then back to Act — or back to Triage when the subsystem assumption was wrong. Dashed boxes are skippable. Click a node or a card.

WHEN TO RUN

Run when the user wants something done: implement, fix, refactor, add, wire, review-and-change. Skip factual questions, “what is X”, and read-only explanation with no change.

/2Triagerequired

Note

/3Actrequired

Ship the smallest reversible diff that fixes the root cause once, using the current repo's conventions.

Do
Climb the ponytail ladder (YAGNI): ask whether the change needs to exist at all, reuse what is here, then ship the minimum code that works. One guard in the shared function beats a guard per caller.
Skip

Note

/4Verifyrequired

Do

Skip

Note

Do

Skip

Note

Do

Note

//GLOSS  TERMS · ACRONYMS · SKILL NAMES[ + ]

Glossary

Short labels used on this page and in the skills. Hover dotted underlines for a one-line expansion; full definitions below.

Process & skills
YAGNI

You Aren't Gonna Need It. Do not build features, abstractions, or "for later" scaffolding until a real task needs them today. First rung of the ponytail ladder: ask whether the change needs to exist at all.

ponytail

Skill that enforces the smallest working diff: YAGNI → reuse existing code → stdlib → one line → minimum fix. Governs what to build, not whether you are allowed to stop.

unlazy

Skill that governs when "done" is allowed. Before Act on substantial work, write observable gates; before claiming complete, run the CHECK and capture evidence. Confidence is not proof.

CHECK / EXPECT

A gate pair from unlazy. CHECK = a command in this repo that can fail (test script, linter, curl). EXPECT = a string that appears in the output only on success. Failed CHECK → Repair, same CHECK again.

Grill · grill-with-docs

Step 1.5: before touching code, align fuzzy words with the project glossary (e.g. withdraw vs delete). Writes canonical terms to glossary.md, not into the repo's CONTEXT.md.

Compound · compound-fix

Step 7: after a fix, file the reusable pattern into gotchas.md if the next person would hit the same trap. Patterns compound; ticket diffs do not.

Triage

Step 2: read the signal in the prompt and pick exactly one search path — grep a literal, graphify symbols, or read the project wiki. Not all three, not a repo tour.

Skills

Markdown playbooks in ~/.cursor/skills/ that tell the agent how to run a workflow — sequence, vocabulary, gates, filing rules.

Knowledge & tools
Graphify

Local tool that builds a code knowledge graph per repo under graphify-out/: classes, methods, files, call paths. Query with code symbols, never ticket titles or symptom sentences.

Second Brain

One name for a vault that implements the LLM-wiki pattern. Not a downloadable app. Create any Obsidian vault and put AGENTS.md + wiki/ in it.

Karpathy LLM wiki

Pattern by Andrej Karpathy: a folder of markdown notes where an LLM agent is the librarian. Source: the gist. You instantiate it; you do not install a product.

Obsidian

Markdown note app used as the IDE for the vault. You browse; the agent edits wiki pages, index.md, and log.md.

MCP

Model Context Protocol — optional plugin servers for agent tools. This stack does not need any: files on disk plus the Graphify CLI are enough.

RAG

Retrieval Augmented Generation — semantic/vector search over documents before the model answers. Skip it until index-first browsing stops scaling (roughly hundreds of pages).

ADR

Architecture Decision Record — a short write-up of a hard-to-reverse choice, stored in wiki/projects/<name>/decisions/.

[[wikilinks]]

Obsidian-style links between wiki pages. Each link is an edge — linked notes beat a flat folder tree for retrieval.

Technical shorthand
Symbol

A code name — class, method, function — used as a Graphify seed. Example: AuthService, runPipeline(). Not a Jira key or error message paraphrase.

Grep / Glob

Grep searches file contents for a literal string (from a stack trace, log line, config key). Glob finds files by name pattern. First triage path when the prompt names a concrete string.

Index-first

Read index.md (the catalog of every wiki page) before opening random notes. Cheap routing — only then load the few pages that matter.

Graph traversal

Follow edges instead of loading everything: wikilinks in the wiki, or call paths in Graphify. The opposite of dumping the whole repo or vault into context.

Diff

The set of line changes git shows between two versions. Review reads the full branch or worktree diff, not only the last commit.

Worktree

A git working directory tied to a branch — may include uncommitted changes. Review covers everything changed on the branch, staged or not.

REST

Plain HTTP APIs. Mentioned only as “you do not need a private API for this stack.”

Gotchas · Glossary · Subsystems

Per-project wiki pages: glossary = canonical terms; gotchas = reusable lessons from past fixes; subsystems = entry symbols for Graphify when you do not know where to start.
